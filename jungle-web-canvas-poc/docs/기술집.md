# Jungle 기술집

Jungle Web Game 개발 중 발견한 외부 기술/오픈소스 아이디어를 **그대로 복사하지 않고, 현재 구조에 맞게 선별 적용하기 위한 기술 참고 노트**다.

기본 원칙:

- 현재 검증된 gameplay / logical X/Y / geometry contract를 우선한다.
- 외부 프로젝트의 전체 아키텍처를 들여오기보다 **가치 있는 알고리즘·표현·패턴만 선택적으로 도입**한다.
- 새 dependency는 실제 효과가 분명할 때만 추가한다.
- Android WebView / 저사양 태블릿을 고려한다.
- 성능 수치는 추측하지 않고 profile-first로 판단한다.
- 도입 전 작은 PoC → 실제 플레이 체감 확인 → 본 적용 순서를 따른다.

## 1. Jakubantalik/thinking-orbs

- Repository: https://github.com/Jakubantalik/thinking-orbs
- Homepage: https://orbs.jakubantalik.com
- License: MIT
- 기술: TypeScript, 2D Canvas 기반 애니메이션
- 용도: AI/agent UI용 dotted thought-orb loading / state indicator
- 상태: `working`, `searching`, `solving`, `listening`, `connecting`, `weaving`, `composing`, `breathing`, `shaping`
- 기본 크기 preset: 64px / 20px

### 핵심 구조

기본 `ThinkingOrb` 컴포넌트는 React 기반이지만, 별도 `thinking-orbs/engine` entry point가 있다.

`thinking-orbs/engine`은:

- React 의존 없음
- DOM 의존 없음
- 순수 geometry/frame 계산
- frame마다 최종 `dots` / `lines` 데이터를 반환
- Canvas, OffscreenCanvas, React Native Skia, custom renderer 등에 연결 가능

따라서 Jungle에는 React 컴포넌트 전체를 가져오기보다 **engine만 활용하거나 동일한 아이디어를 vanilla JS로 얇게 포팅**하는 방향이 적합하다.

### Jungle 적용 판단

**판정: ADOPT NOW — 단, 전체 라이브러리 UI가 아니라 선택적 효과 시스템으로 사용**

Jungle의 핵심 렌더러는 그대로 Three.js/WebGL을 유지한다.
Thinking Orbs는 월드 렌더러를 대체하지 않고 다음과 같은 **HUD / 상호작용 / 포획 연출 보조 효과**로 사용한다.

| Jungle 상태 | Thinking Orbs 상태 | 적용 아이디어 |
|---|---|---|
| 평상시 탐험 | `breathing` | 탐험 감지기 idle |
| 단서 근처 | `searching` | 근처에 단서가 있음을 표시 |
| 새소리 / 소리 단서 | `listening` | 청각 탐색 상태 |
| 퀴즈 진행 | `solving` | 문제 풀이 상태 |
| 여러 단서 연결 | `connecting` | 흔적 연결 연출 |
| 포획 시작 | `weaving` | 새 주변 에너지 / 관찰 집중 |
| 포획 성공 | `shaping` → `composing` | 성공 → 도감 등록 전환 |
| 도감 등록 | `connecting` | 새 정보가 도감에 저장되는 연출 |

### 가장 먼저 적용할 위치

#### 1순위 — 새 포획 Quiz

플레이 루프:

```text
새 발견
  ↓
searching
  ↓
문제 시작
  ↓
solving
  ↓
2/3 이상 성공
  ↓
weaving → shaping
  ↓
포획 성공
```

현재 Jungle에서 부족한 "새를 잡았다"는 손맛과 시각 피드백을 강화하는 데 가장 효과가 크다.

#### 2순위 — 도감 등록

```text
새 portrait
  ↓
connecting orb
  ↓
도감 카드 공개
```

#### 3순위 — 탐험 HUD

작은 오브를 하나만 유지하고 상황에 따라 상태를 변경한다.

```text
평상시      breathing
단서 근처   searching
새소리      listening
문제         solving
```

단순 loader가 아니라 **탐험 감지기**라는 게임 시스템으로 해석한다.

### 렌더링 방식

#### Phase A — 가장 빠른 PoC

별도 작은 2D Canvas overlay.

```text
Three.js World
    │
    ├─ 기존 gameplay
    ├─ 기존 EffectSystem
    └─ Thinking Orb Canvas Overlay
```

장점:

- Three.js gameplay/rendering 변경 최소화
- 실패해도 쉽게 제거 가능
- 태블릿 성능 비교가 쉬움
- 기존 HUD에 독립적으로 붙일 수 있음

#### Phase B — Three.js 월드 통합

효과가 검증된 이후에만 검토한다.

```text
Thinking Orb Engine
       ↓
OffscreenCanvas
       ↓
THREE.CanvasTexture
       ↓
THREE.Sprite / Plane
```

이를 이용하면 단서, 새, 도감 포인트 근처에 실제 3D 월드 오브처럼 띄울 수 있다.

### Jungle 스타일 변형

원본은 monochrome AI UI 디자인이므로 그대로 사용하면 게임보다 AI loader처럼 보일 수 있다.

원본 알고리즘을 유지하되 Jungle 테마에 맞게 색/입자 느낌을 바꾼다.

예시:

- Camp: 연두 / 노랑
- Waterfall: 청록 / 하늘
- Cave: 보라 / 연두
- Giant Tree: 금색 / 초록
- Sky Ridge: 하늘 / 별빛

원본의 `dots` / `lines` geometry만 사용하고 최종 색은 Jungle renderer가 결정하는 방향을 우선한다.

### 성능 / 접근성 참고

thinking-orbs 원본 구현의 좋은 패턴:

- plain 2D canvas
- WebGL/filter 불필요
- DPR cap 2
- `prefers-reduced-motion` 대응
- offscreen 시 `IntersectionObserver`로 pause
- hidden tab에서 animation pause

Jungle에 적용할 경우에도 이 원칙은 참고할 가치가 있다.

특히 태블릿에서는 항상 animate하지 말고 **필요한 순간에만 활성화**하는 것을 우선한다.

### 하지 않을 것

현재 단계에서는 다음을 하지 않는다.

- React 추가
- Thinking Orbs가 Three.js renderer를 대체
- 기존 particle/effects 전체 교체
- 9개 상태 전부 사용
- 화면 곳곳에 여러 orb 인스턴스 생성
- gameplay geometry와 orb geometry 결합
- Orb 도입 때문에 stage progression 변경

초기에는 `searching`, `listening`, `solving`, `connecting`, `shaping` 중심으로 4~5개 상태만 사용한다.

### 구현 후보 파일

PoC 예시:

```text
src/effects/thinking_orb.js
src/effects/thinking_orb_presets.js
```

또는 npm package를 실제 도입할 경우:

```text
thinking-orbs/engine
```

단 현재 프로젝트는 vanilla ES module + Three.js 구조이므로 **React peer dependency 경로는 사용하지 않는다.**

### 적용 게이트

다음 순서로 판단한다.

1. 새 포획 Quiz overlay에 1개 적용
2. PC browser 체감 확인
3. 태블릿 WebView FPS / 입력 지연 확인
4. 기존 Three / particle / audio와 충돌 없는지 확인
5. 만족할 경우 도감 등록/탐험 HUD로 확장
6. 월드 내 CanvasTexture 적용은 마지막에 별도 PoC

### 현재 평가

- 시각적 효과: 높음
- Jungle gameplay 적합성: 높음
- 구현 난이도: 낮음~중간
- 기존 Three.js 영향: 낮음
- Android WebView 위험: 낮음 (overlay 방식 기준)
- 우선 적용 가치: **8.5 / 10**

**결론:** 새 포획 Quiz + 도감 시스템과 함께 작은 Canvas overlay PoC로 적용한다.

## 2. vibe-stack/super-terrain — Mesh Terrain Lab

- Repository: https://github.com/vibe-stack/super-terrain
- 기술: Three.js `WebGPURenderer`, React Three Fiber, TypeScript, worker 기반 terrain compiler
- 성격: 4 km × 4 km 논리 월드를 section 단위로 편집/컴파일/streaming 하는 browser-first mesh terrain editor
- 특징: editable mesh, sculpt layer, weight material, live CSG, tunnel, 5단계 geometric LOD, worker compilation, residency/LRU, IndexedDB persistence
- 중요한 제약: **WebGPU only, WebGL fallback 없음**

### 활용 가능 범위

**판정: POC LATER — production renderer 도입이 아니라 terrain architecture/algorithm 참고용**

현재 Jungle은 Three.js/WebGL 기준으로 실제 플레이와 태블릿 검증이 진행되고 있으므로 `WebGPURenderer` 전환은 하지 않는다. 대신 아래 설계는 향후 지형 고도화 시 참고 가치가 높다.

- terrain을 section/partition 단위로 나누는 구조
- authoritative source와 render output 분리
- worker에서 terrain compilation 후 revision 검사
- stale worker 결과가 최신 terrain을 덮지 못하게 하는 monotonic revision 패턴
- camera 기준 streaming + LRU/residency budget
- screen-error 기반 LOD와 hysteresis
- 기존 mesh를 유지한 채 새 mesh compile/swap
- terrain surface height를 식생/바위/ground-cover가 동일하게 참조하는 ground-following 원칙
- CSG/tunnel/overhang처럼 heightmap만으로 어려운 topology 연구

### Jungle 활용처

#### 1순위 — Waterfall terrain 연구

- 폭포 절벽, 낮은 고저차, 징검다리 주변 terrain 표현
- terrain height sampler를 visual ground-following source로 사용
- player logical X/Y와 collision authority는 그대로 유지

#### 2순위 — Giant Tree / Cave 고저차 연구

- 뿌리/절벽/동굴 입구의 제한적인 local mesh deformation
- 전체 월드를 mesh editor로 바꾸지 않고 특정 landmark 주변만 PoC

#### 3순위 — 대형 맵으로 확장할 때 streaming 참고

현재 5개 stage 규모에서는 과도한 구조다. 향후 한 stage가 매우 넓어질 때만 section streaming / LOD / residency를 검토한다.

### 현재 Jungle에 바로 가져오지 않을 것

- React Three Fiber 도입
- WebGPU renderer 전환
- 4 km sparse world 구조
- terrain editor UI 전체
- IndexedDB terrain authoring persistence
- runtime CSG editor
- worker/LOD 시스템의 선제적 대규모 이식

### 최소 PoC

`waterfall_terrain.js` 또는 별도 실험 파일에서 작은 local terrain patch만 대상으로:

1. 기존 logical X/Y 유지
2. render-only height sampler 적용
3. 바위/나무 약 10~20개가 동일 sampler를 직접 조회해 ground-following
4. 기존 collision/path unchanged
5. PC/태블릿 frame profile 비교

### 적용 게이트

- 현재 WebGL 경로가 유지되는가
- gameplay X/Y/collision contract가 변하지 않는가
- 고저차가 실제 플레이 readability를 개선하는가
- terrain lookup/caching이 profiler에서 병목이 아닌가
- stage별 스케일 불일치를 더 키우지 않는가

**결론:** terrain 기술의 아이디어는 강하게 참고하되, 현재 Jungle production에는 알고리즘 단위로만 선택 적용한다.

## 3. vinhhien112/img2obj — 이미지 → 절차적 Three.js 코드

- Repository: https://github.com/vinhhien112/img2obj
- 참고 글: https://discuss.pytorch.kr/t/img2obj-three-js-codex/11724
- License: MIT
- 기술: Codex plugin + Python 3.10+ + Three.js
- 입력: object/reference image, screenshot, local image path
- 출력: `ObjectSculptSpec` + code-only procedural Three.js factory
- 핵심: pixel-to-mesh 변환이 아니라 **reference 분석 → 구조 명세 → procedural geometry → visual review** workflow

### 활용 가능 범위

**판정: POC LATER — asset authoring/R&D 도구로 사용, runtime 의존성으로 사용하지 않음**

장점:

- object를 component hierarchy로 분해
- geometry/material/pivot/socket을 명시적으로 설계
- blockout → form → lookdev → interaction 단계별 quality gate
- browser render와 reference를 비교하며 수정
- 결과가 코드라 diff/review가 가능
- 움직이는 부품이 있는 소품은 pivot/socket 설계를 처음부터 포함 가능

한계:

- photogrammetry나 정확한 mesh extraction이 아님
- 단일 이미지로 hidden side / 정확 치수 보장 불가
- glass, smoke, liquid, fur, cloth, exact likeness는 추가 reference 필요 가능
- 생성 factory는 완성된 production asset pipeline의 대체가 아님

### Jungle 활용처

#### 1순위 — landmark / prop 제작

- Camp lantern
- 표지판
- 새 perch
- 상자/문/관찰 장치
- Cave crystal prop
- Giant Tree 장식 구조물

#### 2순위 — 식생/바위 procedural reference

- 고목 가지 구조
- 특정 바위 silhouette
- 관목/식생의 구조 연구

#### 3순위 — 새/생물은 제한적으로

새의 body silhouette나 perch pose 연구에는 사용할 수 있으나, production animation/정확한 생물 모델 자동 생성 도구로 보지 않는다.

### Jungle 적용 방식

```text
Reference image
  → img2obj ObjectSculptSpec
  → blockout/form/lookdev review
  → Three.js procedural study
  → 필요한 경우 2D/3D production asset로 재해석
```

현재 game runtime에 plugin을 넣는 것이 아니라 **제작 도구와 quality gate로 사용**한다.

### 최소 PoC

Camp의 작은 prop 1개를 선택한다.

추천:

- lantern 또는 새 perch

검증:

1. reference silhouette 재현
2. 64/96/144px readability
3. 두 번 이하의 bounded correction으로 수렴 가능한지
4. 기존 hand-made/GLB 자산보다 제작시간 또는 수정성이 실제로 좋은지
5. runtime draw call/asset size에 이점이 있는지

### 하지 않을 것

- 한 장 이미지로 전체 stage 자동 생성
- 정확한 캐릭터/새 production mesh 보장 전제
- generated code를 검수 없이 게임에 투입
- img2obj 때문에 현재 gameplay/render architecture 변경

**결론:** Codex와 궁합이 좋은 asset R&D/quality-gate 도구다. 작은 landmark부터 검증하고 성과가 있을 때만 확대한다.

## 4. boona13/mykonos-island-voxels

- Repository: https://github.com/boona13/mykonos-island-voxels
- License: MIT
- 기술: Vanilla ES modules + Canvas 2D, no bundler/no runtime node_modules
- 성격: 14×14 isometric island builder
- 특징: 75+ painterly assets, touch-first mobile input, layered/high-DPI canvas caching, dirty-flag rendering, localStorage auto-save, WebAudio

### 활용 가능 범위

**판정: POC LATER / SELECTIVE BM — Jungle renderer 자체보다 asset/UI/mobile 패턴과 side-game 아이디어 참고**

현재 Jungle은 Three.js 탐험 게임이므로 isometric builder renderer를 가져오지 않는다. 대신 다음 부분은 재사용 가치가 높다.

- asset manifest 중심 구조
- terrain / nature / prop / building 등 명확한 asset category
- 고해상도 source를 display cache로 pre-render 하는 방식
- static layer cache + animation layer만 매 frame 합성
- dirty flag로 idle frame work 최소화
- touch-first pan / pinch / long-press UX
- localStorage save/load의 단순한 progression persistence
- placement sound를 material/category별로 나누는 sound design
- framework 없이 모듈별 책임을 명확히 나눈 코드 구조

### Jungle 활용처

#### 1순위 — 도감/보상 UI와 asset manifest

- 새 도감 카드/이미지 manifest 구조
- stage별 prop/landmark catalog
- asset metadata와 preload/cache 정책 정리

#### 2순위 — 향후 Camp 꾸미기 side-game

탐험 본게임과 별도로:

```text
새 포획/배지 획득
  ↓
Camp에 나무/등불/새집/표지판 배치
  ↓
나만의 탐험 캠프 꾸미기
```

같은 보상 소비형 작은 builder를 만들 때 직접적인 BM 대상이 된다.

#### 3순위 — touch UX 참고

- pinch zoom
- two-finger pan
- long-press delete/secondary action
- mobile safe-area 대응

단 현재 D-pad/A/B 중심 gameplay 조작과 충돌하지 않는 보조 화면에서 우선 활용한다.

### 고성능 렌더링에서 참고할 점

Mykonos는 Canvas 2D지만 다음 원칙은 renderer 종류와 무관하게 참고 가능하다.

- static layer는 변경될 때만 rebuild
- idle frame에서 불필요한 redraw 최소화
- high-DPI cache를 최종 표시 크기에 맞춰 제한적으로 생성
- occupancy/free-cell lookup을 list scan 대신 index 구조로 유지
- asset decode/pre-render는 load 시 처리하고 frame 중 반복하지 않음

### 최소 PoC

Jungle 본게임이 아니라 `bird-codex.html` 또는 별도 `camp-builder-poc.html`에서:

1. 6~10개 prop만 사용
2. 작은 isometric/2D grid
3. touch placement
4. localStorage 저장
5. 모바일/태블릿 입력 체감 검증

### 하지 않을 것

- Jungle 3D world를 isometric Canvas로 교체
- 본게임 path/collision을 TileMap으로 전환
- 75+ asset을 그대로 복사
- editor HUD를 탐험 HUD에 직접 이식
- builder 기능 때문에 현재 새 탐험/퀴즈 progression을 지연

**결론:** 본게임 renderer 기술보다는 **asset pipeline, mobile interaction, cache 전략, 향후 Camp 꾸미기 보조 게임**의 참고 구현으로 가치가 높다.
