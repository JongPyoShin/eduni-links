# Phase 6 — Local two-player factual explanation

Mode: `둘이 두기`

Coach: ON

After each committed move, the coach should display:

```text
이 수로 바뀐 점
```

The explanation must describe observable board state changes only.

Forbidden examples:

```text
상대가 공격하려고 둔 수예요.
연결하려고 둔 것 같아요.
영역을 넓히려는 의도예요.
```

Allowed style:

```text
이 수로 내 돌 1개가 잡혔어요.
이 수로 내 돌 2개가 단수가 됐어요.
이 수로 상대 돌 두 무리가 연결됐어요.
이 수로 잡힌 돌은 없어요.
```

Try to reproduce and verify:

- ordinary move
- capture
- atari
- connection

## Critical perspective check

Do not verify local explanations only by string presence.
Compare each explanation against the actual board state and the player perspective.

Specifically verify that black/white perspective is not inverted.
For example, if Black captures White stones, the explanation must not incorrectly say that Black's own stones were captured.

Any mismatch between the board and `내 돌 / 상대 돌` wording is HIGH or BLOCKER depending on user impact.

PASS only if all materially required checks are verified:

- actual `/baduk` runtime uses shared coach logic

- local two-player post-move explanation works

- full Python tests pass
- Node tests pass
- generated JS syntax passes
- route smoke passes when environment supports it
- 360px UI has no blocking issue when browser QA is available

## CONDITIONAL PASS

Use only for non-blocking issues such as wording or cosmetic layout problems, or for cases where all executable checks pass but an environment-specific browser/deployment check cannot be performed.

## FAIL

FAIL if any of these occur:

- runtime still uses a different coach implementation than the tested logic
- generated JavaScript syntax error
- coach explanation contradicts board state
- local mode guesses human intent
- Baduk engine regression
- board-level switching error
- `/baduk` runtime error
- portal regression
